# Phase 041 — Job Freshness & Discovery Quality

## Mission

Execute Phase 041 across the following repositories:

- `Sriramleo/job-search-api` — FastAPI backend, job discovery, normalization, qualification, and persistence.
- `Sriramleo/job-search` — React/Vite frontend and job-search experience.
- `Sriramleo/homelab-gitops` — Kubernetes deployment and ArgoCD configuration, only if infrastructure changes are required.

Phase 040 reported a healthy production deployment with 137 active opportunities, 141 stored job documents, 22 application records, and zero application submissions.

The purpose of this phase is to improve the **freshness, relevance, provenance, deduplication, and actionability of job opportunities**, rather than perform another broad infrastructure refactor.

The target candidate is an India-based Senior DevOps/Platform Engineer pursuing suitable employment in Germany, with relocation and potential EU Blue Card sponsorship considerations.

Inspect the actual repositories and production state before relying on the reported counts, commits, or architecture.

## 1. Mandatory Safety Constraints

These requirements are hard invariants.

1. Keep campaign stage `STAGE_0_DRY_RUN`.
2. Keep campaign `is_enabled: false`.
3. Do not initiate real manual or automated application submissions.
4. Do not reserve submission quota or acquire application-submission leases.
5. Do not delete or rewrite historical applications, ATS confirmations, or audit events.
6. Do not fabricate job descriptions, salary ranges, source dates, employer evidence, fit scores, or relocation/visa support.
7. Do not treat an HTTP 200 response as proof that a job is still open.
8. Do not mark a job unavailable based solely on a temporary network failure, rate limit, CAPTCHA, access denial, or ambiguous response.
9. Never bypass CAPTCHA, MFA, authentication, anti-bot controls, or employer restrictions.
10. Preserve existing qualification, provenance, freshness, language, duplicate, quota, emergency-stop, and unknown-outcome safeguards.
11. Do not expose MongoDB URIs, API tokens, candidate PII, or credentials in logs or reports.
12. Do not perform bulk production mutations without a verified dry-run preview and an explicit authorization if the mutation is destructive or materially changes historical records.

Before changes, capture read-only baseline evidence. Stop and report any safety-invariant violation.

## 3. Establish a Job Freshness Baseline

Using read-only production queries, establish the actual state of the job catalogue.

Report:

- Total stored job documents.
- Total active/available opportunities under the canonical API filters.
- Archived or unavailable jobs.
- Jobs with unknown freshness.
- Jobs with missing source URLs.
- Jobs with missing provider job IDs.
- Duplicate clusters based on reliable identifiers.
- Jobs whose source timestamps are missing or older than the configured freshness threshold.
- Jobs with a previous verification result and its timestamp.
- Jobs by source/provider and ATS platform.

Use existing schema fields and status semantics wherever possible. Do not invent new timestamps to fill gaps.

Distinguish clearly between:

- `OPEN_CONFIRMED`: authoritative source evidence confirms the posting is open.
- `UNAVAILABLE_CONFIRMED`: authoritative source evidence confirms the posting is expired or unavailable.
- `UNKNOWN`: evidence is insufficient, contradictory, inaccessible, or too old to support a conclusion.

If the project uses different canonical status names, retain those names or introduce a backward-compatible mapping.

Do not assume a previously active job remains open merely because it is present in MongoDB.

## 4. Improve Freshness Verification

Review the existing freshness probes and strengthen them only where necessary.

### Required behavior

1. Prefer official ATS/provider APIs and authoritative employer job pages.
2. Reuse known provider IDs and canonical source URLs.
3. Persist verification timestamps and provenance for freshness results.
4. Distinguish a confirmed expired posting from a temporary verification failure.
5. Avoid repeatedly probing the same URL unnecessarily.
6. Apply bounded timeouts, retries, and rate limits according to provider behavior.
7. Treat redirects carefully; verify that the destination still represents the same vacancy.
8. Avoid interpreting generic HTTP 200 pages, login pages, bot challenges, or generic career pages as proof of an active job.
9. Preserve historical verification evidence for auditability.
10. Ensure failed checks cannot silently promote an unknown job to open or demote an open job to unavailable without sufficient evidence.

If freshness thresholds already exist, document and reuse them. If none exist, propose conservative configurable thresholds and test them; do not hardcode an arbitrary global expiry policy without considering provider semantics.

### Safety rule

An inaccessible source is not equivalent to an expired job.

## 5. Improve Canonicalization and Deduplication

Identify duplicate clusters using evidence in this order where available:

1. Same ATS provider and provider job ID.
2. Same canonical employer job URL.
3. Reliable external requisition identifier.
4. Carefully normalized employer, title, location, and posting metadata.

Do not merge jobs solely because their titles are similar.

Handle:

- Tracking parameters and URL fragments.
- Trailing slashes and safe URL normalization.
- Known ATS URL aliases.
- Reposted jobs with a genuinely new requisition ID.
- The same job discovered through multiple sources.
- Historical legacy IDs and prior duplicate insertions.

Produce a dry-run duplicate report with:

- Proposed canonical record.
- Candidate duplicates.
- Evidence supporting the grouping.
- Which fields would be retained or updated.
- Any ambiguity requiring human review.

**Do not delete or merge production job documents in this phase without explicit authorization.**

Implement or harden idempotent upsert behavior so repeated discovery of the same vacancy does not create new duplicates. Add regression tests for repeated ingestion and conflicting source evidence.

- Relocation support.
- Visa sponsorship or work authorization requirements.

A high technical fit score must not override an expired posting, an unmet mandatory language requirement, missing provenance, or unresolved work-authorization constraints.

Use deterministic, explainable rules for hard requirements. Any scoring changes must have tests and a documented rationale.

## 10. Testing Requirements

Add or update tests covering:

### Freshness
- Confirmed active posting.
- Confirmed expired posting.
- Temporary network error.
- Rate limit and access denial.
- CAPTCHA or bot challenge.
- Generic HTTP 200 page.
- Redirect to a different vacancy.
- Missing or stale timestamps.
- Verification history preservation.

### Deduplication
- Identical provider and job ID.
- Equivalent canonical URLs.
- Tracking-parameter differences.
- Same title but distinct requisition IDs.
- Repeated ingestion idempotency.
- Conflicting source evidence.
- Ambiguous duplicate requiring human review.

### Qualification
- Relevant technical fit with expired posting.
- Missing salary.
- Mandatory language mismatch.
- Unknown relocation or sponsorship evidence.
- Unsupported ATS source.
- High fit score with unresolved hard requirements.

### API and frontend
- Freshness filters and sorting, where supported.
- Correct pagination and total counts.
- Clear empty versus error states.
- Accurate freshness badges and timestamps.
- Preservation of existing job filters and application workflows.

Run relevant existing tests, then the full backend suite, full frontend test suite, and production build where the environment permits.

Do not weaken tests to obtain a passing result.
