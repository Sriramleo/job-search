# Phase 051 — FreeHire Germany Job Discovery Integration

## Objective
Evaluate and, if successful, integrate FreeHire as an additional job-discovery provider into the existing Germany Job Search Dashboard.

Repository: https://github.com/strelov1/freehire
Public API: https://freehire.me/api/v1/jobs
API documentation: https://freehire.me/docs/api

## Architecture constraints
- Oracle/k0s and the existing FastAPI/MongoDB Atlas system remain the source of truth.
- GCP remains the separate AI/orchestration layer.
- Do not deploy the complete FreeHire stack or add another database.
- Do not modify existing application stages, delete historical jobs, or alter existing safety controls.
- Auto-apply remains in STAGE_0_DRY_RUN.
- No unattended application submissions and no outbound recruiter email sending.
- Start with read-only API evaluation.

## Step 1: Inspect FreeHire's live API
Read its current API documentation and determine:
- Supported search endpoints and exact query parameters.
- How country, region, city, remote work, role, skills, seniority, and pagination are represented.
- Whether Germany can be selected directly or must be matched using supported facets.
- Response schema, job-description availability, source URLs, freshness fields, and rate limits.
- Whether any API fields require authentication.

Do not invent endpoint parameters. Use only the documented contract.

## Step 2: Benchmark Germany job coverage
Search for:
- Senior DevOps Engineer
- DevOps Engineer
- Platform Engineer
- Site Reliability Engineer
- Cloud Infrastructure Engineer
- Kubernetes Engineer
- Cloud Platform Engineer

Prioritize Germany-based roles and remote roles explicitly available from Germany.

Use supported country/region filters and relevant skill searches. Follow pagination and API rate limits.

Produce a benchmark report containing:
- Total results by role and query.
- Unique jobs after deduplication.
- Jobs with official employer application URLs.
- Jobs with complete descriptions.
- Jobs whose Germany location can be verified.
- Jobs confirmed open through authoritative evidence.
- Relevant opportunities absent from the existing dashboard.
- Duplicate rate, inaccessible URLs, stale listings, and unknown cases.

Do not report unverified results as open or relevant.

## Step 3: Compare against production data
Read the existing job inventory through the approved backend interface.

Compare FreeHire results against existing records using canonical application URL, ATS posting ID, company, normalized title, location, and existing identifiers.

Create a dry-run import manifest. Do not write production records during the benchmark.

## Step 4: Integration criteria
Proceed with a provider adapter only if the benchmark demonstrates meaningful additional relevant Germany-based opportunities.

The adapter must:
- Preserve FreeHire's source attribution and original job URL.
- Preserve existing canonical IDs and MongoDB unique-index guarantees.
- Normalize fields into the existing schema.
- Use idempotent ingestion and bounded batches.
- Respect rate limits and back off on HTTP 429.
- Handle missing descriptions and location data without fabrication.
- Send imported jobs through the existing Germany eligibility, freshness, deduplication, and AI qualification pipeline.
- Keep UNKNOWN freshness distinct from JOB_UNAVAILABLE.
- Avoid duplicate scheduled jobs or unnecessary AI calls.

Do not allow FreeHire's fit score or open-status claim to bypass the existing verification gates.

## Step 5: Deliverables
Provide:
1. API contract and supported filters.
2. Benchmark results with representative source URLs.
3. Incremental job coverage versus the current inventory.
4. Duplicate and freshness analysis.
5. Cost estimate and operational impact.
6. Dry-run import manifest.
7. Recommendation: integrate, investigate further, or reject.
8. Tests and files changed, if any.

Stop after the read-only benchmark and dry-run manifest. Request review before production ingestion or schedule changes.
