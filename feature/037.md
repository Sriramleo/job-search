## 7. Stage E — Quota, lease, and submission-safety audit

Verify the actual production implementation and configuration of each safeguard.

### Daily quota

- Daily maximum is one application.
- Confirmed, attempted, locked, unknown-outcome, and remaining-capacity values are consistent.
- Inspect the quota record for the current production-local date.
- Verify that dry-run evaluation did not reserve or consume a real-submission slot.

### Execution lease

- Inspect the lease acquisition and release implementation.
- Verify a competing worker cannot execute the same campaign concurrently.
- Verify lease expiry and recovery cannot cause a duplicate submission.
- Do not deliberately launch a real submission worker or risk production state to test concurrency.

Use existing isolated automated tests or safe non-submitting verification for concurrency behavior.

### Emergency stop

- Confirm the production emergency-stop state.
- Inspect the code path showing that an enabled emergency stop prevents campaign execution.
- Use isolated tests for latch behavior; do not toggle production state unnecessarily.

### Submission idempotency and unknown outcomes

Verify that:

- `SUBMISSION_INITIATED` is persisted before any final submit action.
- Unknown outcomes lock the slot and cannot automatically retry.
- Only positive ATS confirmation permits the terminal Submitted/Applied state.
- Duplicate detection is repeated immediately before any future authorized submission.
- Quota reservation is atomic and respects company/day and ATS/day limits.
- Stale worker recovery cannot reset an uncertain submission to a retryable state.

Inspect tests, implementation, audit records, and deployed behavior. Do not perform a live submit to prove these safeguards.
