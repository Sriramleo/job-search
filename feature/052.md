# Phase 052 — Integrate FreeHire Direct-ATS Discovery into job-search-api

## Authorization and objective
Proceed with implementing the production FreeHire discovery adapter, based on the Phase 051 benchmark.

Repository: https://github.com/strelov1/freehire
API base: https://freehire.me/api/v1

Use the existing job-search-api discovery pipeline. Do not deploy or self-host the full FreeHire stack.

## 1. Strict source allowlist
Initially allow only these source types when they can be verified from authoritative evidence:
- Greenhouse
- Personio
- Ashby
- Lever
- Workday
- SmartRecruiters
- Pinpoint
- JOIN

Do not trust a FreeHire-provided source label alone. Validate the actual destination hostname and application URL against a maintained provider-specific allowlist.

Reject aggregator and broker destinations, including Adzuna and WhatJobs. Reject unknown providers and redirect-only URLs that cannot be resolved safely to an approved employer ATS destination.

Do not bypass login requirements, CAPTCHA, MFA, access controls, or anti-bot restrictions.

## 2. Read-only provider client
Implement a dedicated FreeHire client that:
- Uses the documented API contract and supported Germany filters.
- Sends an identifiable User-Agent.
- Implements timeouts, bounded retries, exponential backoff, and rate-limit handling.
- Respects pagination and API quotas.
- Handles malformed responses and missing fields safely.
- Logs request counts, latency, failures, and source attribution without exposing secrets.

Do not invent API parameters or assume undocumented response fields.

## 3. Eligibility and evidence
Every discovered record must pass the existing Germany eligibility, freshness, deduplication, and qualification pipeline.

Preserve:
- Original FreeHire record identifier.
- Original listing URL and canonical application URL.
- Verified provider and hostname.
- Company and job title.
- Location and work model.
- Description and its provenance.
- Discovery and verification timestamps.
- Freshness classification and unknown fields.

A FreeHire listing is a discovery signal, not proof that a job remains open. Revalidate through the approved official ATS or employer career page before treating it as VERIFIED.

If authoritative verification fails or is inconclusive, use the existing UNKNOWN or JOB_UNAVAILABLE rules appropriately.

## 4. Safe ingestion and deduplication
- Reuse existing canonical job schema and repository patterns.
- Deduplicate using canonical application URL, ATS posting ID, company, normalized title, and location as appropriate.
- Preserve the unique custom-ID index and existing MongoDB `_id` values.
- Use idempotent ingestion and bounded batches.
- Never overwrite richer verified fields with weaker FreeHire data.
- Never delete or merge historical records.
- Do not change application stages or fabricate application outcomes.

First run the adapter in dry-run mode and generate a proposed-import manifest.

## 5. Controlled production rollout
Use two separate stages:

A. Dry run:
- Run the adapter against the existing 43 reported net-new senior direct-ATS candidates.
- Revalidate each candidate.
- Report accepted, rejected, duplicate, stale, and unknown counts.
- Show representative records and source evidence.
- Make zero production writes.

B. Bounded ingestion:
- After reporting the dry-run results, stop and request review before enabling production writes.
- Following approval, ingest only eligible records in bounded batches.
- Start with a small batch and verify database/API/UI consistency before continuing.
- Add a feature flag and emergency stop.
- Keep the provider independently disableable without affecting existing sources.

Do not silently activate ingestion as part of deployment.

## 6. Monitoring and cost
Track:
- Jobs discovered.
- Unique jobs after deduplication.
- Approved direct-ATS records.
- Verification success and unknown rates.
- Aggregator and invalid URL rejection counts.
- Incremental relevant jobs added.
- API latency, failures, and rate limits.
- AI tokens and cost per useful verified opportunity.

Do not run Gemini qualification for records already rejected by deterministic source, geography, freshness, or duplicate gates.

## 7. Preserve existing safety controls
- Auto-apply remains STAGE_0_DRY_RUN and disabled.
- No unattended applications.
- Outbound recruiter email remains hard-disabled with HTTP 403.
- Gmail remains read-only.
- Unknown submission outcomes block retries.
- Candidate facts and employer evidence must not be fabricated.
- No direct GCP-to-MongoDB access.

## 8. Tests and delivery report
Add tests for:
- Allowed and disallowed provider hostnames.
- Redirect and URL validation.
- Germany eligibility.
- Duplicate detection and idempotency.
- Rate limiting, timeout, and retry behavior.
- Missing and malformed source fields.
- Freshness classification.
- Dry-run zero-write guarantees.
- Feature-flag disablement and emergency stop.
- Existing application and outreach safety invariants.

Run the relevant backend regression suite and report deployment commits, tests, manifests, and actual production state.

Do not report completion until the live deployment is verified. Keep production ingestion disabled until the dry-run evidence is reviewed.
