## 4. Phase 042B — Bounded Freshness Recovery

### Target selection

Select at most 30 high-priority jobs from the existing qualified opportunities, prioritizing:
- Senior DevOps Engineer
- Senior Platform Engineer
- Site Reliability Engineer
- Cloud Platform Engineer
- Kubernetes / Infrastructure Platform Engineer

Prefer roles in Germany that have a usable official ATS vacancy URL and strong existing candidate-evidence-based qualification results.

Do not invent qualification evidence, employer requirements, salary information, or job status.

Before probing, save a read-only list of the selected job IDs and the reasons for selection. Do not change job ranking or qualification records merely to make a job eligible for verification.

### Probe limits

Implement or reuse a bounded worker with:
- Maximum 30 unique jobs per execution.
- Maximum 2 concurrent external requests.
- A configurable per-host rate limit and minimum request interval.
- Explicit connection and total request timeouts.
- Exponential backoff with jitter for transient errors.
- `Retry-After` support when supplied by the provider.
- A persistent execution lease or equivalent guard preventing overlapping freshness runs.
- A maximum retry budget per job per execution.
- Safe handling of process restart and partial failure.
- No automatic repeated probing of a job already successfully verified during the configured freshness window.

Do not add Redis. Reuse the project's existing persistence and scheduling approach.

If the current environment lacks a suitable scheduler, implement the worker and document the scheduling configuration. Do not create a new external cloud resource without authorization.

### Freshness classification

Preserve the existing status model where possible.

- `VERIFIED` / verified active: affirmative evidence that the specific vacancy remains open.
- `JOB_UNAVAILABLE`: authoritative vacancy-specific evidence of closure or expiration.
- `UNKNOWN`: evidence is inconclusive.
- `STALE`: freshness has exceeded the configured age threshold; stale is a freshness-age property, not proof of closure.

At minimum, ensure:
- HTTP 403 and 429 remain unknown.
- CAPTCHA, anti-bot challenges, authentication redirects, timeouts, and transient 5xx errors remain unknown.
- Generic company career pages do not count as proof that a specific vacancy is active.
- A vacancy-specific 404 or 410 is evaluated with provider-aware logic before declaring it unavailable.
- An official ATS page that affirmatively identifies the specific vacancy as open can count as active.
- Transient failures never erase a prior successful verification timestamp or historical evidence.
- Each attempt records a timestamp, verification method, result, and concise reason. Store HTTP status when available.
- Avoid logging response bodies that could contain personal data, tokens, or sensitive information.

Do not downgrade a previously verified job based only on a transient failure.

### Execution and reporting

Run the worker once against the selected target list after tests pass.

Report:
- Number selected and attempted.
- Number verified active.
- Number confirmed unavailable.
- Number unknown or still stale.
- Counts by ATS provider and failure reason.
- Request totals and retries.
- Whether rate limits or access restrictions prevented completion.
- Evidence that no application submissions or quota reservations occurred.

Do not claim freshness recovery succeeded if probes were not actually executed against production.

## 5. Phase 042C — Prevent New Duplicate Job Records

Inspect every write path that can create or update jobs, including:
- Discovery providers
- Qualification batches
- Imports
- Direct ATS discovery
- Scheduled background jobs
- Manual or administrative ingestion endpoints

Enforce a consistent, idempotent write strategy across these paths.

### Matching order

1. Reliable provider identity plus provider job ID.
2. Normalized canonical vacancy URL.
3. Employer, normalized title, and location as a corroborating match, not sufficient evidence for an automatic merge when ambiguity remains.

Normalize tracking parameters such as `utm_*` and known non-identity referral parameters only when it is safe to do so. Preserve query parameters that identify the actual vacancy, including Greenhouse tokens and other provider-specific identifiers.

Never replace a verified official ATS URL with a generic aggregator URL.

When a match is reliable:
- Update the existing record through an atomic upsert.
- Preserve original provenance and important historical verification evidence.
- Update `last_seen_at` only when the source actually observed the vacancy.
- Do not overwrite stronger source information with weaker evidence.
- Do not create a second document for the same canonical vacancy.

When a match is ambiguous:
- Preserve the incoming record as a candidate for manual review, or skip creation according to the existing documented ingestion policy.
- Record why the match was ambiguous.
- Never silently merge two potentially different requisitions.

### Regression tests

Add tests proving:
- Repeated ingestion of the same vacancy does not increase document count.
- Provider identity matches correctly.
- Tracking parameter variants normalize correctly.
- Provider-specific vacancy tokens are preserved.
- Official ATS URLs are protected from aggregator overwrite.
- Similar titles at the same company do not cause unsafe merges.
- Existing application references remain unchanged.
- Concurrent ingestion does not create duplicate records where the chosen database strategy claims to prevent it.

If duplicate custom IDs currently exist, do not assume `upsert_one` by custom ID has resolved the historical problem. Inspect MongoDB indexes and the actual write query. Explain whether distinct MongoDB `_id` values share the same custom `id`.
