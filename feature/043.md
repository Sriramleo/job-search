**Project:** German Job Search Dashboard  
**Execution:** Inspect existing implementation, make changes, test, deploy, and verify production.  
**Approach:** Preserve historical data, reuse existing services, avoid unrelated refactoring.

## 2. Jobs Page — Replace Fit Labels With Percentages

Replace labels such as `Strong Fit`, `Moderate Fit`, and `Weak Fit` with percentage scores.

Requirements:
- Display a clear percentage, such as `85%`, instead of the categorical label.
- Identify the actual existing numeric score and its scale before implementing the change.
- Convert a score to a percentage only when the mapping is mathematically valid and documented.
- If no valid numeric score exists, display `Not evaluated` or an equivalent neutral value. Never invent a percentage.
- Preserve the existing qualification evidence, hard blockers, unknown requirements, and explanations.
- Make the score accessible in the Jobs table and preview drawer.
- Keep the UI consistent on desktop and mobile.

If multiple scores exist, inspect the schema and display the correct overall fit percentage. Keep salary, location, technical fit, and readiness details separate when they represent different dimensions.

Add tests for score conversion, missing scores, boundary values, and legacy records.

## 3. Remove Manual/Automatic Submission Routing From the Jobs Page

Remove the Jobs page controls, route options, or buttons that allow users to choose between manual submission and automatic submission.

The Jobs page should focus on:
- Discovering opportunities.
- Reviewing fit percentages and qualification evidence.
- Checking freshness and location.
- Opening the official ATS job/application page.
- Reviewing job details.

Do not remove legitimate application history or the existing submission-method information from the Applications page.

Do not introduce a new automatic submission path through the Jobs page.

## 4. Hide Applied Jobs From Active Jobs and Show Them in Archive

When a job has a corresponding application with stage `Applied`, it must no longer appear in the active Jobs list. Show it in the existing Archive page, or implement an appropriate archive view if none exists.

Requirements:
- Preserve the job document and application record.
- Do not delete jobs or rewrite historical application details.
- Maintain the application-to-job relationship.
- Ensure the job remains accessible through the archive and application detail views.
- Keep rejected applications and other historical outcomes accessible.
- Ensure an ambiguous or unknown submission outcome is not automatically treated as a successful application.
- Ensure `AUTO_APPLY_READY` or a prepared application is not treated as `Applied`.
- Handle multiple application records associated with one job safely.
- Make active job counts, archive counts, pagination, and sidebar counters consistent.

Use the canonical application stage as the source of truth. Do not infer that an application was submitted solely because a preparation workflow ran.

Add tests proving that:
1. A genuinely `Applied` job is hidden from active Jobs and visible in the archive.
2. A job without an applied application remains active when otherwise eligible.
3. Rejected applications remain visible in application history.
4. Unknown submission outcomes are not silently marked as Applied.
5. Archiving does not mutate or delete historical records.

## 5. Gmail Sync — Automatically Detect Rejection Emails

Improve the existing Gmail read-only sync and application outcome classifier so that relevant rejection emails update the correct application to `Rejected`.

### Matching requirements

Use the available evidence in this order where appropriate:
- ATS application or requisition identifiers.
- Known employer and job title.
- Application confirmation or email thread references.
- Sender and message context.
- Existing application timeline and outcome history.

Do not rely solely on a sender address or a generic word such as “unfortunately.”

### Classification requirements

Recognize genuine rejection messages in English and German, including common expressions such as:
- “We regret to inform you…”
- “We will not be moving forward…”
- “Your application was unsuccessful.”
- “Leider müssen wir Ihnen mitteilen…”
- “Wir haben uns für andere Kandidaten entschieden.”

These are examples, not sufficient evidence on their own. Use the complete relevant message context and application match.

Distinguish:
- Rejected.
- Interview invitation.
- Assessment request.
- Application received or confirmation.
- Request for additional information.
- General recruitment updates.
- Ambiguous or unmatched emails.

### Safe state transitions

- Update an application to `Rejected` only when the message is sufficiently conclusive and matches the correct application.
- Record the source email/thread reference, classification reason, and processed timestamp in the existing audit/timeline model.
- Make synchronization idempotent so that reprocessing the same email does not duplicate events or repeatedly alter application state.
- If a rejection conflicts with newer authoritative application evidence, preserve the evidence and flag the conflict for review rather than silently overwriting it.
- Route ambiguous messages to the existing review queue.
- Keep Gmail read-only. Never send, reply to, delete, or modify emails.
- Do not print email bodies or unnecessary personal information in logs.

Add regression tests using representative English and German email fixtures, including false positives, unmatched messages, duplicate syncs, and conflicting outcomes.

Verify the result by synchronizing available production messages and reporting counts for processed, rejected, unmatched, and needs-review emails. Do not fabricate a rejection or claim that a live rejection was found if none exists.

## 6. Germany-Only Job Filtering

The active Jobs page must show only roles explicitly relevant to Germany.

Requirements:
- Include jobs located in Germany.
- Include remote jobs only when Germany is an explicitly supported work location.
- Exclude US-only, US-remote, and other non-Germany-specific jobs.
- Do not assume a role is Germany-eligible merely because the employer has a German office.
- Use structured location fields first, then reliable source evidence.
- If location eligibility cannot be determined, label it unknown and exclude it from the Germany-only active view until reviewed.
- Preserve source URLs and original location evidence.
- Avoid incorrectly excluding Germany-based roles just because the company is headquartered elsewhere.

Apply the filter consistently to:
- Backend job queries and counts.
- Jobs page results and filters.
- Discovery and qualification ingestion where appropriate.
- Dashboard counters and pagination.
- Archive views where the relevant filtering behavior is intended.

Provide a reason for each excluded job, such as `US_ONLY`, `REMOTE_US_ONLY`, `NON_GERMANY_LOCATION`, or `LOCATION_UNKNOWN`.

Do not delete excluded jobs. Keep existing records intact and use filtering/archive semantics appropriate to the data model.

Add tests for Germany-based jobs, Germany-eligible remote jobs, US-only roles, other-country roles, and ambiguous locations.

## 7. Discover Jobs From Official Company Career Pages

Extend the existing company careers discovery implementation rather than building a duplicate discovery system.

Inspect `company_careers.py`, existing ATS integrations, discovery scheduling, and ingestion paths first.

Requirements:
- Discover relevant jobs from official employer career pages and supported ATS endpoints.
- Prioritize official structured ATS APIs or feeds when available.
- Support existing ATS providers and extend coverage only where practical.
- Discover DevOps, Platform Engineering, SRE, Cloud Infrastructure, Kubernetes, and related senior engineering positions in Germany.
- Preserve provider identifiers, official vacancy URLs, employer identity, location evidence, discovery timestamps, and source provenance.
- Prefer official direct ATS application URLs over aggregator URLs.
- Apply Germany eligibility and existing qualification rules before presenting jobs as relevant opportunities.
- Use idempotent ingestion so repeated discovery does not create duplicate job documents.
- Respect rate limits, timeouts, retry budgets, robots/access restrictions, and provider terms.
- Do not bypass authentication, CAPTCHA, MFA, or anti-bot protection.
- Do not mark a generic careers homepage as a verified open vacancy.
- Do not fabricate job descriptions, locations, salary information, or vacancy status.

Report the actual number of career pages and providers inspected, jobs discovered, unique vacancies added, existing vacancies updated, duplicates avoided, and failures.

If the current source configuration does not contain an appropriate set of official employer career pages, document the gap and implement a small, maintainable seed list based on existing configuration patterns. Do not introduce unrelated paid services or new cloud resources without authorization.

## 8. Auto-Apply Scheduler — Inspect Existing Implementation First

Determine whether the auto-apply scheduler and submission workflow already exist. Inspect the actual code, deployment, scheduler configuration, campaign state, quota/lease logic, and execution logs.

Do not assume a scheduler is implemented merely because Cloud Scheduler, Cloud Run, the ADK agent, or a campaign service exists.

If already implemented:
- Verify the schedule, target, authentication, lease handling, quota enforcement, emergency stop, and current execution mode.
- Confirm that the scheduler cannot submit applications while the campaign is disabled.
- Check for duplicate scheduled jobs or overlapping executions.
- Verify the configured daily cap and unknown-outcome locks.
- Report the existing configuration and gaps; avoid rebuilding it unnecessarily.

If missing or incomplete:
- Implement or complete the safe scheduled workflow for discovery, qualification, freshness checks, and application preparation.
- Reuse the existing Oracle/k0s FastAPI backend, GCP Cloud Run ADK agent, Cloud Scheduler, and established identity boundaries.
- Do not introduce Redis or an alternative architecture.
- Ensure scheduler invocations are authenticated, idempotent, bounded, observable, and protected against overlapping runs.

### Critical application-submission boundary

The current production campaign must remain:
- `stage = STAGE_0_DRY_RUN`
- `is_enabled = false`
- Real application submissions = 0
- Active submission quota leases = 0

Do not enable live automatic application submission, perform real ATS form submissions, or advance the campaign to Stage 1 in this phase.

The scheduled workflow may discover, qualify, verify, prepare, and queue applications for human review. Real submission requires separate explicit authorization and must not be activated as a side effect of this phase.

The GCP agent must not send Gmail or perform LinkedIn automation. Gmail remains read-only.
