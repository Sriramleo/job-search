## 3. Resolve the 141-versus-137 Job-Count Discrepancy

This is the highest-priority investigation.

### 3.1 Establish authoritative counts

Using read-only queries against the verified production database, record:

- Total documents in `db.jobs`.
- Distinct job IDs.
- Distinct canonical URLs or provider IDs where available.
- Documents missing required identifiers.
- Documents that cannot be normalized by the current `Job` schema.
- Counts by status, source, and relevant pipeline stage where fields exist.

Do not dump full documents or sensitive fields into logs.

### 3.2 Trace the API count semantics

Inspect the implementation of `GET /api/jobs` and determine:

- Whether the response contains a total count, returned count, or page count.
- The default page size and pagination parameters.
- Whether filters are applied before or after counting.
- Whether duplicate suppression changes the total.
- Whether schema-invalid documents are excluded or cause failures.
- Whether enrichment changes identifiers, statuses, or eligibility.
- Whether the database query and count query use identical filters.
- Whether frontend pagination defaults explain the 100 returned records.

Use the API's actual response schema and implementation rather than assuming field meanings.

### 3.3 Reconcile the four-record difference

Produce a sanitized reconciliation showing how 141 stored documents map to the API's reported 137 opportunities.

For every excluded or unrepresented record, record only the minimum necessary metadata, such as internal ID, reason category, source, and normalization outcome.

Classify each difference with evidence, for example:

- Duplicate record.
- Deliberately filtered record.
- Invalid legacy document.
- Excluded status.
- Count-query inconsistency.
- Pagination misunderstanding.
- Other verified cause.

Do not invent a category or reason merely to make the numbers balance.

### 3.4 Correct only confirmed defects

If the database and API disagree because of a code defect:

1. Add a focused regression test.
2. Fix the query, normalization, filtering, or count logic at the narrowest appropriate layer.
3. Preserve existing API compatibility unless a documented contract defect requires a change.
4. Avoid destructive data cleanup.
5. If a data migration is necessary, first produce a dry-run report and stop for authorization before executing it.

The final report must explicitly reconcile all counts or mark the discrepancy unresolved.

## 4. Harden Legacy Job Normalization

Review the Phase 039/legacy job-schema fix.

Validate that mappings such as these are deterministic and safe:

- `company` → canonical company field.
- `url` or `applicationUrl` → canonical source URL.
- `atsProvider` → appropriate source and ATS metadata.
- Salary range text → salary minimum/maximum only when supported by reliable source data.
- Fit scores → canonical evaluation fields only when the original semantics are known.
- Legacy evidence status strings → valid evidence enums only when their meanings are equivalent.

Requirements:

- Missing optional fields must not crash list serialization.
- Required identity fields must not be fabricated.
- Unknown evidence values must not be falsely promoted to verified evidence.
- A fallback must not imply a real salary, qualification, application submission, or employer confirmation.
- A normalization failure must be observable and auditable without exposing PII.
- Per-item error handling must not silently conceal a systematic data-integrity problem.

Add tests for representative legacy documents and malformed edge cases.

## 5. Verify Job Discovery and Qualification

Audit the discovery pipeline without triggering uncontrolled scraping or application activity.

Confirm:

1. Discovery creates or updates canonical job records idempotently.
2. Provider job IDs and canonical URLs are used to prevent duplicates.
3. Repeated ingestion does not create additional records for the same real-world vacancy.
4. Stale and archived jobs are handled according to existing policy.
5. Job freshness is based on supported source timestamps, not fabricated timestamps.
6. ATS URLs and source provenance are retained.
7. Qualification and fit scoring remain separate from submission-method classification.
8. Missing salary or relocation evidence does not become a fabricated positive qualification.
9. The recent legacy-field normalizers do not inadvertently make unsuitable jobs eligible.
10. Existing freshness, provenance, relocation, language, and duplicate gates remain intact.

Do not run a broad discovery campaign unless necessary and explicitly authorized. Prefer fixtures, controlled tests, and read-only inspection.

Report discovery defects separately from API count defects.
