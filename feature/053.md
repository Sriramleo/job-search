## Objective

## Phase A — Read-only investigation
1. Inspect the existing LinkedIn discovery adapter, source configuration, scheduled jobs, pagination, retries, and deployment configuration.
2. Reproduce the supplied search using authorized access. Respect LinkedIn authentication, rate limits, terms, and anti-bot controls. Never bypass CAPTCHA, MFA, access controls, or anti-bot challenges.
3. Establish the actual job cards returned. Do not assume the currentJobId parameter represents the complete search results.
4. Compare discovered cards against production records using LinkedIn job ID, canonical URL, and normalized company/title/location.
5. Trace each missing record through:
   - Source discovery
   - Parsing and normalization
   - Germany and role eligibility
   - Seniority, employment type, salary, and other configured filters
   - Freshness and availability validation
   - Deduplication and archive rules
   - MongoDB persistence
   - API response
   - Frontend filtering, sorting, pagination, and status tabs
6. Inspect scheduler execution history, logs, and the deployed commit. Distinguish an actual production failure from a code-level possibility.

## Phase B — Evidence report
Produce a table with one row per investigated job:
- LinkedIn job ID and URL
- Company, title, and location
- Present in source results?
- Present in MongoDB?
- Present in API response?
- Visible in frontend?
- Exact stage where excluded
- Evidence and recommended action

Summarize counts and root causes. If the full LinkedIn result set cannot be retrieved, state the access limitation and do not invent missing-job counts.

## Phase C — Fix only verified root causes
After reporting findings, implement minimal targeted fixes for confirmed defects, with regression tests. Do not loosen legitimate Germany, seniority, freshness, or qualification criteria merely to increase job counts.

Keep existing job IDs and historical records intact. Do not create duplicate discovery adapters if the current source can be repaired.

## Safety and deployment
- Initial audit is read-only.
- Do not write to MongoDB during Phase A or B.
- Do not apply for jobs, submit forms, contact recruiters, or send emails.
- Do not enable auto-apply or change outreach restrictions.
- Do not enable FreeHire background polling as part of this phase.
- Do not bypass access controls or anti-bot protections.
- Require an explicit operator decision before production data changes or deployment.

## Completion criteria
Provide the root cause, evidence, affected-job counts, test results, exact files/commits changed, and verification plan. Do not claim production verification without live evidence.
