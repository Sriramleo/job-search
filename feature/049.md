# Phase 049 — Production Data Reconciliation and End-to-End Smoke Test

## Objective
Independently verify the live German Job Search Dashboard after Phases 044–048. Resolve discrepancies between MongoDB, backend API responses, dashboard counters, archive filters, and scheduled agent execution.

## 1. Inspect before modifying
- Read the Phase 044–048 completion reports and existing project instructions.
- Inspect the current GitOps deployment, backend and frontend versions, API contracts, MongoDB schemas/indexes, and current production data.
- Record a baseline of job counts, application counts and stages, company counts, freshness statuses, outreach drafts, and campaign configuration.
- Do not assume prior completion reports prove the current live state.

## 2. Reconcile the job-count discrepancy
Investigate why Phase 045 reports 108 active Germany-eligible jobs and 46 archived/ineligible jobs, while Phase 048 reports 154 active jobs and zero archived jobs, with 108 shown in the active UI.

Verify:
- MongoDB records grouped by their actual status and eligibility fields.
- Backend active-job and archive endpoint filters.
- Frontend list filters, pagination, and sidebar counters.
- Whether the numbers use different definitions of active, eligible, and archived.

Document the root cause with actual API responses and database aggregation results. Do not assume the discrepancy is merely a UI issue.

## 3. Preserve production data
- Do not delete, merge, or silently reclassify historical job or application records.
- Preserve existing MongoDB `_id` values and the unique custom `id` index.
- Do not change application stages or fabricate freshness verification.
- If a data migration is necessary, first produce a dry-run report, explain the exact proposed changes, and require explicit authorization before production writes.
- Make no unrelated schema or architecture changes.

## 4. Run a read-only end-to-end verification
Verify:
- Job discovery and Germany eligibility filtering.
- Freshness states: VERIFIED, JOB_UNAVAILABLE, and UNKNOWN.
- Duplicate prevention and unique-ID integrity.
- Active/archive UI and API counts.
- Application history and stage counts.
- Outreach draft approval, suppression, quotas, and cooldown behavior.
- Campaign disabled state and rejection of outbound email requests.
- Gmail remains read-only.
- Google Cloud Scheduler execution, Cloud Run health, logs, and the Oracle agent/API boundary.

Do not trigger a real application submission or send an email. Use read-only checks and safe dry-run tests. Avoid running production workflows merely to generate test activity.

## 5. Validate safety invariants
- Auto-apply remains disabled in STAGE_0_DRY_RUN.
- AUTO_APPLY_READY is not proof of submission.
- An unknown submission outcome blocks retries.
- CAPTCHA, MFA, authentication challenges, and anti-bot checks cause the workflow to stop rather than be bypassed.
- No candidate facts, employer evidence, work authorization, or privacy consent may be fabricated.
- Outreach draft approval does not authorize email delivery.
- GCP remains an ops/AI layer and does not access MongoDB directly.

## 6. Report and exit criteria
Produce a Phase 049 completion report containing:
1. Baseline and final counts, with definitions.
2. Evidence for every endpoint, database aggregation, and scheduled-agent check.
3. Root cause of the job-count discrepancy.
4. Tests executed and pass/fail results.
5. Any unresolved issues and risks.
6. Exact files and commits changed, if any.
7. Explicit confirmation that no real applications or emails were sent.

Do not claim PASS if the discrepancy remains unexplained or the live state could not be verified. If a production mutation is required, stop after preparing the proposed migration and request authorization.

## Architecture constraints
Oracle/k0s remains the source of truth for job search, MongoDB, matching, application lifecycle, and Playwright. GCP Cloud Run/ADK remains a separate ops/AI layer using the read-only Oracle Agent API. Preserve the existing architecture and historical data.

Begin with inspection and read-only verification. Do not implement new features until the reconciliation findings are complete.
