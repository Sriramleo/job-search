# Phase 039 — Production Verification, Application Data Integrity & Human Review Workflow

## Mission

Execute Phase 039 across both repositories:

- `Sriramleo/job-search-api` — FastAPI backend
- `Sriramleo/job-search` — React/Vite frontend

Phase 038 implemented submission-method classification, application filtering, sorting, and UI cleanup. Phase 039 must verify those changes against real production data, validate the deployed API/frontend contract, fix any confirmed defects, and strengthen the human-review workflow.

**This is a verification and hardening phase only. Do not submit applications, enable automation, change the campaign stage, or bypass human decisions.**

Follow the existing repository architecture, coding conventions, deployment workflow, and safety policies. Inspect the actual implementation before making assumptions.

## 1. Mandatory Safety Constraints

Treat the following as hard invariants throughout the entire phase.

1. Campaign remains `STAGE_0_DRY_RUN`.
2. Campaign `is_enabled` remains `false`.
3. Do not enable Stage 1 or authorize real application submissions.
4. Do not initiate manual or automated submissions during tests, smoke tests, or production verification.
5. Do not create, delete, or mutate application records just to make tests pass.
6. Preserve all 17 existing production application records and their history.
7. Do not alter historical application outcomes, ATS confirmations, timestamps, or audit events unless fixing a specifically demonstrated data-integrity defect through a safe, auditable migration.
8. Do not infer `AUTO` from `AUTO_APPLY_READY`, fit score, campaign eligibility, or readiness percentage.
9. Never infer German work authorization from EU Blue Card eligibility or willingness to relocate.
10. Never accept a privacy notice or consent checkbox on the candidate's behalf.
11. CAPTCHA, MFA, authentication challenges, anti-bot controls, and ambiguous external submission outcomes must retain their existing safety handling.
12. Never retry an application when its external submission outcome is unknown.
13. Do not expose personal information, credentials, access tokens, or private application data in logs, test artifacts, or the final report.

Before and after production verification, capture read-only evidence of the campaign configuration, application count, key historical records, and submission counters. If an invariant is violated, stop immediately and report the discrepancy. Do not attempt a broad rollback or destructive repair without authorization.

## 3. Submission-Method Classification Integrity

Audit the classification logic for all supported states.

### Required classification rules

- `AUTO`: Actual automated submission execution with positive external ATS confirmation and reliable provenance.
- `MANUAL`: Explicitly recorded human submission through the established manual workflow.
- `UNKNOWN`: Historical submitted record without sufficient reliable evidence of the submission method.
- `None` / `—`: Not submitted.

Verify that:

- Readiness states and fit scores never imply a submission method.
- An application that is `AUTO_APPLY_READY` but has not been submitted remains unsubmitted.
- A submitted historical record with missing method provenance is not silently classified as `AUTO` or `MANUAL`.
- Legacy fields are normalized consistently without silently overwriting authoritative stored values.
- The UI badges and API values agree.
- An application cannot be marked `AUTO` solely because a confirmation-like string exists without valid submission evidence.
- A failure or unknown outcome cannot be displayed as a successfully submitted application.

Inspect the actual persisted production records before proposing any data migration.

If correcting legacy data is necessary, prefer a read-only report or dry-run migration first. Do not execute a bulk production migration without a demonstrated need and explicit authorization.

## 4. Application API Contract Verification

Test `GET /api/applications` against the deployed API using read-only requests.

Verify the following parameters and their documented behavior:

- `submissionMethod=ALL`
- `submissionMethod=AUTO`
- `submissionMethod=MANUAL`
- `submissionMethod=UNKNOWN`
- `sortBy=submittedAt`
- `sortBy=submissionMethod`
- `sortBy=stage`
- `sortOrder=asc`
- `sortOrder=desc`

Also inspect pagination, existing search filters, stage filters, status filters, and default behavior.

### Required checks

1. The API accepts only supported parameter values or handles invalid values through the project's established validation convention.
2. Existing filters compose correctly with submission-method filtering.
3. Counts correspond to the intended result set and are not accidentally computed only from the current page.
4. Database-level and in-memory filtering/sorting produce equivalent results.
5. Legacy `appliedDate` fallback is deterministic and documented.
6. Applications without a submission timestamp remain at the bottom for both newest-first and oldest-first date sorting.
7. Equal timestamps produce deterministic ordering using a stable secondary key.
8. Sorting by method and pipeline stage uses explicit, documented ordering.
9. Empty results and missing optional fields do not cause frontend failures.
10. No request changes production application data or campaign state.

Inspect the implementation carefully before deciding whether `UNKNOWN` and unsubmitted records are mutually exclusive filter categories. Preserve the documented API semantics and make the UI labels unambiguous.

## 9. Fix, Commit, Deploy, and Verify

If the audit finds confirmed defects:

1. Make the smallest safe fix.
2. Add a regression test reproducing the defect.
3. Run the relevant tests, then the full suites.
4. Review the final diff for accidental data changes, secrets, and unrelated refactoring.
5. Commit directly to `main`, following the project's established workflow. Do not create a feature branch unless repository policy requires one.
6. Push the changes.
7. Deploy using the established production deployment process.
8. Verify the deployed commit/image/version where the system exposes it.
9. Repeat read-only health, API-contract, UI, and safety-invariant checks.

If no defect is found, do not create meaningless code changes merely to produce a commit.

Do not claim that a deployment is complete based solely on a successful local build or an HTTP 200 response.

Never run destructive database operations, alter candidate answers, or enable application submission as part of this phase.
