# Phase 038 — Application Management Filters, UI Cleanup & Submission Readiness

## Mission

Implement the next application-management improvements following Phase 037:

1. Add filters to distinguish manually submitted applications from automatically submitted applications.
2. Improve sorting and visibility of application submission history.
3. Remove unnecessary, redundant, confusing, or obsolete UI elements.
4. Preserve application records, audit history, and all existing automation safety controls.
5. Keep the SumUp Data Platform Engineer application in human review; do not submit it or enable Stage 1.

Work directly on `main` in both repositories:
- `Sriramleo/job-search-api`
- `Sriramleo/job-search`

Do not create feature branches or force-push.

## Stage A — Preflight and current-state audit

Before changing anything:

1. Pull and reconcile the latest `origin/main` in both repositories.
2. Inspect the existing Applications page, Application Workspace, submission-history fields, API schemas, campaign dashboard, and related tests.
3. Identify how the application system currently records:
   - Manual submissions.
   - Automated submissions.
   - Applications prepared but not submitted.
   - Applications awaiting human review.
   - Failed submissions.
   - Unverified or unknown submission outcomes.
4. Determine whether a reliable submission-method field already exists. Reuse it if possible.
5. Capture the production application count and verify the historical SumUp, 1KOMMA5°, and Wandelbots records.
6. Record the current campaign configuration and deployed Git revisions.

Do not assume that an application was automated merely because it passed `AUTO_APPLY_READY`. Submission method must describe what actually happened.

## Stage B — Submission-method classification and filtering

Add an application submission-method classification that supports at least:

- `MANUAL`
- `AUTO`
- `UNKNOWN` for legacy records whose method cannot be established reliably.

Use the project's existing naming conventions if an equivalent field already exists.

### Data and API requirements

1. Inspect the actual submission event, audit history, and application record before assigning a method.
2. Persist the method when the submission workflow can establish it reliably.
3. Manual submissions must be recorded as manual, including cases where an application was prepared by the system but submitted by the user.
4. Automated submissions must be recorded as automatic only when the automation actually performed the submission and the required positive ATS confirmation was obtained.
5. Do not infer the submission method from readiness state, fit score, creation date, or current application stage.
6. Preserve `UNKNOWN` for historical records without adequate evidence. Do not backfill guesses.
7. Ensure API responses expose the method and support filtering without breaking existing clients.

### Frontend requirements

Add a visible filter to the Applications page:

- All submissions
- Manual submissions
- Auto submissions
- Unknown method, where relevant

Also provide a clear way to sort the application list by:

- Most recently submitted.
- Oldest submitted first.
- Submission method, if useful and consistent with the existing UI.

Requirements:

- Use the actual submission timestamp rather than record creation time.
- Keep the selected filter and sort stable through refreshes, pagination, and other application filters where feasible.
- Make it clear that `AUTO_APPLY_READY` is a readiness state, not proof of automatic submission.
- Distinguish submission method from application status: Applied, Preparing, Submission Failed, Submission Unverified, and other existing states.
- Ensure the filter works with server-side pagination if the current architecture uses it.
- Do not create duplicate application records to support filtering.

## Stage C — Remove unwanted UI elements safely

Audit the Applications page, Application Workspace, and Campaign Dashboard for unnecessary or redundant items.

Identify:
- Duplicate status indicators.
- Repeated information that is already clearly shown elsewhere.
- Obsolete controls or labels left behind by earlier phases.
- Empty or misleading fallback cards.
- Unnecessary buttons that do not perform a useful action.
- Confusing distinctions between readiness, submission status, and campaign state.
- Debug-only elements that should not be visible in production.
- Dead UI components or unused controls confirmed by code inspection.

Before deleting anything, verify that it is genuinely redundant or obsolete.

### Cleanup rules

1. Do not remove useful application history, audit records, error details, safety warnings, emergency-stop controls, or human-review actions.
2. Do not remove any control needed to prevent duplicate submissions or recover an unknown outcome safely.
3. Do not hide important blockers merely to simplify the interface.
4. Do not remove campaign controls solely because auto-apply is currently disabled.
5. Prefer targeted cleanup over a complete UI redesign.
6. Keep the interface responsive, accessible, and consistent with the existing design.
7. Document the elements removed or consolidated and explain why.

### Work authorization

The Greenhouse form asks whether the candidate is authorized to work in Germany.

- EU Blue Card eligibility alone must not be treated as an existing work permit or unconditional current work authorization.
- Do not automatically select `Yes` based only on relocation plans or Blue Card eligibility.
- Do not automatically select `No` without establishing the meaning of the employer's question and relevant circumstances.
- Preserve the question as `HUMAN_INPUT_REQUIRED` until the candidate's actual status and the employer's sponsorship requirements are clarified.
- Do not invent or silently submit an answer.

### Privacy consent

- Keep the privacy-notice checkbox unchecked unless the user has explicitly consented to that notice.
- Display the relevant notice and require affirmative human consent before any future submission.
- Do not interpret previous approval of the automation system as blanket consent to employer-specific privacy terms.

### Submission boundary

- Do not activate Stage 1.
- Do not invoke any final submission action.
- Do not create an application record that implies SumUp was submitted.
- Do not reserve a real-submission quota slot.
- Keep the candidate available for human review with its verified evidence and unresolved answers clearly displayed.

## Stage E — Safety and historical integrity

Preserve all existing campaign protections:

- Duplicate detection and provider-ID reconciliation.
- Freshness and ATS provenance gates.
- Fit threshold of at least 85%.
- Readiness threshold of at least 90%.
- Daily maximum of one real application.
- Durable atomic quota reservation.
- Execution lease and concurrency protection.
- Emergency stop.
- `SUBMISSION_INITIATED` persistence before any future final submit action.
- `OUTCOME_UNKNOWN` lockout with no automatic retry.
- Positive ATS confirmation before marking a submission as complete.

During Phase 038:

- Keep campaign stage `STAGE_0_DRY_RUN`.
- Keep `is_enabled: false`.
- Submit zero real applications.
- Preserve historical application records and audit history.

2. Confirmed automated submissions appear under the Auto filter.
3. Legacy records with unknown method remain Unknown rather than being guessed.
4. Readiness state alone never classifies an application as Auto.
5. Submission timestamps control submission-date sorting.
6. Filters compose correctly with existing search, status filters, and pagination.
7. Filtering never creates, deletes, or mutates application records.
8. Cleanup does not remove required safety controls or human-review actions.
9. The SumUp work-authorization answer remains unresolved without verified human input.
10. Privacy consent is not fabricated.
11. Campaign remains disabled and no real submission action is invoked.
12. Existing Phase 031–037 functionality remains intact.

Run focused tests first, then the full backend regression suite, frontend test suite, and production build. Report actual results and exit codes.
