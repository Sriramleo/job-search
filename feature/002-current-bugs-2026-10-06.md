## BUG-001 — Manual submission recording fails for preview application

### Observed
The UI shows:

"Manual submission recording failed: Application 'preview-qual-job_disc_a458150c5b71' not found."

The error occurs from the **Confirm Manual Submission** flow after clicking **"Yes, I submitted it"**.

### Expected
- The confirmation action must resolve the application record that is displayed in the current workspace.
- If the application is a preview/draft application, the UI/backend must use a valid persistent application ID or prevent confirmation until the application has been persisted.
- The user must never receive a misleading successful-looking loading state followed by a raw "application not found" alert.
- Error handling should clearly explain what happened and leave the application in a safe, recoverable state.

### Acceptance criteria
- Reproduce with a preview application.
- Trace frontend application ID → API request → backend lookup → MongoDB record.
- Fix the ID/persistence mismatch.
- Add regression tests.
- Verify normal manual-submission confirmation still works.
- Verify no historical applications are modified.

## BUG-002 — Remove/clean up unavailable jobs

### Requirement
If a job is verified as unavailable/stale/removed, clean it up from the active job experience.

### Expected behavior
- Detect unavailable jobs using semantic freshness verification, not HTTP 200 alone.
- Do not delete immutable application/history/audit records.
- Mark unavailable jobs with an appropriate terminal/archived state.
- Remove them from active/recommended job lists.
- Preserve provenance so the system knows why and when the job became unavailable.
- If a job becomes available again, allow safe reactivation only after fresh verification.

### Acceptance criteria
- JOB_UNAVAILABLE jobs do not appear as active recommendations.
- Historical applications remain untouched.
- Audit/provenance is preserved.
- Stale SPA shells such as the previously identified Ashby case are handled correctly.

## BUG-003 — Latest jobs must appear first

### Requirement
All job/discovery lists should default to newest-first ordering.

### Expected behavior
- Sort by the most reliable discovery/verification timestamp, with deterministic fallback.
- New jobs must appear before older jobs.
- Pagination must preserve the ordering.
- Frontend must not reorder results incorrectly after receiving API data.

### Acceptance criteria
- API default ordering is newest-first.
- Frontend job lists show latest jobs first.
- Pagination does not produce older records before newer records unexpectedly.
- Add regression tests for mixed timestamp fields and pagination.
